# 新增输入的局部准备与已验证产物复用

2026-11-01。仅隔离开发版；正式应用、存档、设置、已有缓存及 Release 不变。

## 已确认的问题

用户第二次普通启动使用了正确的私有 QA 缓存根。新捕获的 `.meta` 触发整批准备登记的严格变化检查，这个回退本身合理，但后续局部复用没有真正启用：`prepare_game_psos` 只从生产 `RuntimeProfile` 获取调度代码身份；私有双后端 QA 没有这个对象，因此 `code_identity=None`，已有的逐管线 `Recipes` 永远没有建立。实际队列结果为 `recipe_schedule=null`。

这轮本机库准备 51.273 秒（357 跳过、70 新建）；模块准备 44.680 秒；完整 PSO 队列 105.115 秒（362 原生产物命中、67 新建，但 scheduled_reused=0）。Metal 准备合计约 206.7 秒。模块与 PSO 位于 game-preparation 内，不与其父阶段重复累加。模块层虽然已有源代码提取复用，仍重复读取和验证冻结输入、原生输出与目标关联。

## 实际修改

- 私有 QA 从实际加载的完整工具闭包取得同一调度身份，启用原有逐管线队列。生产流程继续使用原 `RuntimeProfile`；不伪造配置，也不改变编译器、完整输入或运行时键。
- 新增管线仍走原生准备和最终验证；旧管线只有完整输入、真实 native worker、DSO、布局、选项、环境及对应库/归档证明都匹配时才免 worker。整批变化检查没有放宽。
- 模块层记录原完整校验成功后的精确依赖集合；绑定原编译器、校验实现、源目录连续变化记录、当前完整特化及实际目标。后续仅在依赖文件及模块输出目录身份均未变时复用，不再重读冻结数据和重复校验全部输出。文件替换、同尺寸修改、输出目录增项、符号链接、身份变化及源变化记录丢失均走原校验。
- 未选中的有效证明保留，支持 A→A+B→B→A；新增无关模块或报告不使旧证明整体失效。GS 不被强行纳入不支持的证明路径。
- 准备报告增加有限的拒绝原因和原生模块校验复用数，用于核对是否真正采用；没有新增逐帧诊断。

## 验证边界

146 项相关定向回归通过，包括依赖变化、输出目录增项、校验期间修改、源历史丢失、实际工具闭包身份及原整批调度校验。真实 FSEvents 测试在允许访问系统变化记录的执行环境通过；没有修改这些测试来绕过失败。

另以真实缓存的独立 APFS 副本、原 native worker 和真实 Metal DSO 执行 A→A+B→A：首次两个输入产生 2 份证明；新增一个输入时复用 2、实际队列仅处理 1 并登记 1；切回原两个时复用 2、work_units=0。无拒绝。此验证没有启动游戏，不是启动时间、探索路线或内存验收。

下一步集中验证隔离包连续启动与真实探索捕获后的重启，记录到场景耗时、模块子进程、管线 worker、现场编译和峰值/持续内存。首次为旧缓存补登记的时间必须与后续暖启动分开。不得将上述小规模原生控制当作整场景测试。


## 真正的旧模块迁移遗漏与补修

集中启动验证发现，旧缓存保留的真实 packet/receipt 路径仍指向之前的已登记 QA 缓存。原完整校验可以采用这些产物，但新复用登记只接受当前目录，因此没有为它们建立证明。不能通过改写 packet、重算收据或把它们当成当前路径解决。

补修限定为同一隔离 state、合法 QA GPU 目录、同一完整 compiler 身份下，索引明确指向的单个 generic 模块 case。它必须有原 input/packet.json、output/result.json、output/module.spv 的准确关系。仍须先通过全部原校验；随后绑定真实文件和 input/output 目录身份，以及当前源目录连续变化记录。不同 state、不同 compiler、别名路径和目录增项均拒绝。typed companion 和 GS 的额外准入没有放宽。

真实已登记产物的离线控制：411 个 generic 模块首次完整验证 48.864 秒，第二轮全部 411 个采用证明，耗时 0.613 秒。没有启动游戏或 native worker，没有失败项。这只证明这一段校验的复用，不是完整启动或 FPS 验收。

## 游戏启动测试尚未验收

- 真实隔离队列：393 个 plain 管线直接复用，36 个 GS 管线保留原验证；native 批次从 27 降为 3，队列阶段从首次 53.091 秒降至 20.187 秒。GS 证明尚未扩展，不能称所有管线均跳过。
- 这次续测在旧模块迁移补修之前进行：模块阶段仍为 46.453 秒，到场景约 128.004 秒。不能拿这个数字当补修后的暖启动结果。
- 测试副本最初漏带 FEX 缓存，误触发无关 CPU 首次编译，已主动中止并保留对象。补入相同兼容身份的缓存后，原生产器确认 export/scanner/compiler 均为 0。
- 已进场景，但本批交换相对原基线增长约 2302 MiB，触发既有 2 GiB 保护，完整 45 秒样本未完成。正式数据未修改、原 QA 存档校验未变化。不得将中止运行称为验收通过。
- 后续游戏测试等待本批保护容量确认；不重置原保护基线来绕过中止。代码和定向验证继续推进。补修后的连续启动、探索捕获后重启和峰值/持续内存仍待完成。
