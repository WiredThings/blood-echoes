# 静态同码条目的完整输入与运行时按需采用

## 实现范围和来源

静态目录中发现 350 组指令字节和硬件阶段相同、程序标识不同的记录，共 954 个身份。这不是全部可准备的游戏管线数量。

本轮先支持 Fragment 和 Compute：目标与来源必须有唯一且一致的完整静态头信息，只排除已验证的文件内代码重定位寄存器；代码 SHA 和独立读取的实际字节必须相等。完整运行状态、资源特化、SRT 与用户数据来自已有真实编译输入，不生成描述符、不合并不同状态，也不宣称目标将以这个状态执行。每个目标／Profile 先选一个完整上下文。

这是“静态代码证据 + 已知完整上下文”的自动构造类别。没有历史上下文的新安装，以及代码不同、信息不完整的类别，仍明确保留缺口，由正常运行捕获继续补充；不能宣称纯静态全游戏覆盖。

## 已接入的路径

1. `static_variant_inputs` 复用原 `freeze_module`、游戏源读取与完整特化构造。
2. 原生 module worker 用**目标**程序标识重新编译，核对重新生成的 SRT 和完整特化，并输出新 SPIR-V 与新生成的模块元数据。
3. SPIR-V 发射器会写入一条未被引用的 `OpString(program hash)` 来源标记，因此不同程序标识的结果不必逐字节相同。本类别只允许该一处标记变化，其余模块头、ID、调试数据和全部语义指令仍必须逐字一致；参考与实际二进制均不改写。原普通模块路径继续要求完整字节相等。结果明确保留 `expected_spirv_equal=false` 和限定的差异证明，不冒充完整字节相同。哈希专用行为（包括 buffer-copy 回写）若改变实际指令，将被拒绝。
4. 完整管线输入复用原实际管线上下文，只替换目标阶段及其新分配的槽位标识，其他字段保留，交回原审计、准备队列、Metal 库与管线归档流程。没有另建编译器或管线调度器。
5. 新模块存于所选 GPU 数据目录的 `automatic-game-inputs/static-native-variants`。记录按实际编译器映像、Profile、硬件阶段、程序标识和实际代码 SHA 区分；旧产物保留，损坏记录保留后局部重建。
6. GPU 在加载阶段绑定只读目录，实际首次使用程序时才读取一个有界记录。先核对实际代码、Profile、编译器和完整运行状态，再受保护地读取当前资源，重新构造完整特化；匹配且后端对象创建成功后才发布。失配回到原编译路径，不跳绘制、不替换资源、不扩大已有对象缓存。

沿用原本机准备 auto/load 选择；off/record 不采用此记录。未使用模块不整批预载，GUI 无需新增独立功能开关。Metal、内存、速度图、遮挡、页表、汉化、联网、F2/F3 及 CPU 后端流程未重新实现。

## 当前验证及边界

- 新增 21 项定向检查，连同原模块、自动 GPU 准备及封闭脚本依赖回归，共 72 项通过。
- 5 个真实同码条目已完成原生重新编译及限定差异证明；对应新模块元数据通过真实布局解码，可生成 5 份完整管线输入。单个打包模块记录约 12–16 KiB，不能据此推断整场景内存收益。
- 标准 native 目标构建完成；使用标准 metadata-layout 目标完成当前 ABI、序列化和源文件绑定验证。
- **尚未完成**：打入新隔离 QA、实际场景采用／现场编译对照、峰值和持续内存对照。原生控制与定向测试不能代替这些验收。
- 尚未更新正式应用或 Release；正式存档、设置、原缓存未改动。

本轮收尾只做上述实现的打包与集中验收，不扩展新的推断类别。现有草动画问题及其他 CPU 后端工作保留。
