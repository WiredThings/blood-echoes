# 首次上传的 CPU 摘要与 GPU 内容保护

## 现场与边界

2026-10-28 在用户确认故障仍存在时，分别保存狗和持武器村民的实际采样 view：16 和 26 个完整读回，均检查 GPU 完成和文件写入成功。村民这次达到单请求 16 MiB 上限，不宣称穷尽全部绑定。游戏纹理、截图和详细记录只留本机私有诊断目录。

匹配网格的一组动态材质呈彩噪，另一组内容正常。对故障候选物理对象，早期 GPU 复制／用途升级前后的三个局部样本一致，后续一次刷新上传的三个样本则与采样前完整读回对应位置一致。后续上传输入的前 128 字节与初始输入头一致；这不是整段 CPU 内存从未改变的证明。两条狗靠得太近，出画面对照不能独立区分它们，不将这一步作为归因证据。

该证据把问题缩小到后续刷新重新采用旧内存内容的路径。它不是“所有白模均已修复”的结论，安装后仍需正常探索和战斗复测。

## 已复现的源码缺口

`TextureCache::RefreshImage` 原先只在 `GpuModified` 已设置时记录 `mip_hashes`。普通采样纹理的首次 CPU 上传没有该标志；`ExpandImage` 的新目标也先刷新 CPU 数据，再复制有效 GPU 内容并继承 GPU 标志。

因此，纹理后来已经持有 GPU 生成的有效内容，CPU 摘要却仍是初始化值。再次收到 `CpuDirty` 时，即使 CPU 内容未变，也会被当成新数据上传，覆盖 GPU 像素。已有“从一开始就作为 storage 绑定”的回归覆盖不到这个顺序。

修正是在每次实际刷新上传时保留各 mip 的 CPU 摘要，包括尚未 GPU 修改的首次上传。现有规则保持：GPU 修改后、CPU 摘要相同且没有 `GpuDirty` 时才跳过；CPU 真实变化仍上传，`GpuDirty` 仍强制采用缓冲区来源。只改共享 TextureCache 一个编译对象。

## 成本与兼容性

使用已有 `mip_hashes`，不新增持久字段、GPU 对象、缓存或历史纹理引用。未脏纹理仍在原入口直接返回，没有增加逐绘制摘要计算。新增成本发生在原先不记录摘要的实际 CPU 刷新上传；尚未测量其完整游戏加载耗时，不能宣称零成本。

不修改纹理格式、采样器、着色器翻译、管线键、两级页表、速度图、遮挡剔除、联网、F2/F3 或资源回收策略。不清空、重建或缩小缓存。应用替换只涉及代码和相应组件签名／摘要，不修改正式存档、设置或缓存。

## 定向验证

`test_texture_cpu_baseline.mm` 使用真实 TextureCache、Metal 上传／清除／扩展和像素读回，数据全部自制：

- 普通纹理：GPU 修改后，未变 CPU、真实 CPU 更新、`GpuDirty` 三项。
- 扩展纹理：上述三项，加仅更新尾 mip、保留 GPU 主 mip 一项。

旧后端在两条未变 CPU 路径及尾 mip 反例中，都会错误恢复旧主 mip；其余更新对照通过。修正后七项全部通过。实际载入库路径已核对，Metal 验证层开启。

另外通过原有首次上传三项、扩展四项、生成链六项、完整读回十项，共 30 项新后端 GPU 回归。生命周期测试仍检查旧 backing 的 weak 引用最终释放。这些是定向像素／兼容性验证，不代替游戏内白模复测、帧率或持续内存验收。

复用现有测试入口：

```sh
python3 tools/run_texture_probe_test.py --cpu-baseline \
  --compile-commands /path/to/renderer/compile_commands.json \
  --library /path/to/private/libbbgpu.dylib
```

在隔离开发状态目录运行，游戏退出后再编译和执行。摘要见 `evidence/texture-cpu-baseline-20261028/summary.json`；不发布包含私有捕获的安装包。
