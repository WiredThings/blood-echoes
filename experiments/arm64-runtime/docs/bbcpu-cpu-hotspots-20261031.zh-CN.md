# bbcpu CPU 损耗归因：2026-10-31

## 结论与边界

已发现有实际对照支持的接入热点：bbcpu 高频进入动态执行时，经共用可执行范围查询反复获取全局锁；FEX 的相同场景中，这条查询链很少出现。当前证据优先支持优化接入与查询调度，不能直接认定 bbcpu 的静态重编译天生只有 FEX 一半性能，也没有把完整帧率差距分摊完。

这次是两轮**诊断**，不是新的优化收益对照。每轮完整观察至少45秒场景，在进入场景10秒后运行一次 `/usr/bin/sample PID 10 5`；bbcpu 另开原有 `BB_RECOMP_TARGETS=1`（目标按1/64抽样）。计数及栈分析扰动时序，记录的18.64/44.88 FPS不得取代之前无分析器的20.9/47.9–48.8 FPS基线，也不据此声称收益。Cua仅用于测试前选择原前端，运行前已停止；无截图、录屏或战斗输入，全程静音。

两轮设置三份SHA完全相同、镜头均(-190.784,-27.226,71.116)、绘制中位数1135/1134；GPU均值19.88/19.33ms。bbcpu使用与原基线完全相同的337628832字节静态库，SHA为`c741d0a0d088d55de7c7b2ac288d1cde758c19efdde4d6bea6a039bcbf1d6dbd`，241046/241046准入、0 changed。两轮均完成后由已有监护协议结束143，无保护中止，源QA存档摘要保持；正式应用、存档、设置和已有缓存未改，未发布Release。

## 代码范围查询：首要接入热点

按同一Darwin调用树方法逐线程统计，self计数在全部线程上完整覆盖线程观察数；递归祖先每个叶样本只计一次。主游戏线程由独立的游戏执行线程识别，不是Cocoa主线程。下表是**采样窗口中的线程墙钟栈观察比例**，包含阻塞，不能作为CPU执行时间、可回收帧时间或直接FPS增益；不同祖先类别也不可任意相加。

| 可识别的查询链 | bbcpu | FEX |
| --- | ---: | ---: |
| 主游戏线程 | 341/1009 = 33.80% | 7/826 = 0.85% |
| GXRenderThread | 82/1009 = 8.13% | 1/826 = 0.12% |
| GXWorker 1–5 | 17.54–23.89% | 0.12–0.48% |

bbcpu主游戏线程的204/1009（20.22%）样本直接停在查询链的`__psynch_mutexwait`；图形工作线程也反复阻塞在该链。实际路径：

`run_translated / bbcpu_jit_run / call_import` → `bbcpu_is_guest_code` → `BbcpuBackend::Query` → `HleCallService::QueryExecutableRange` → `game_runtime.cpp::executable` → `HleVeneerAllocator::QueryExecutableRange`（先取allocator_mutex）→ 必要时State共享锁及范围查找。

上游默认的bbcpu范围判断可以直接遍历已登记范围；当前embedding安装了动态query回调，替换了它。FEX有先查线程已登记范围的路径，并可复用已生成执行代码；它也不是完全不加锁，不能把差异简化为“FEX零校验”。真正的问题是bbcpu的高频执行过渡反复进入共用带锁路径。

优先候选：复用已有的、具有明确生命周期与权限依据的可执行范围；稳定范围命中不再每次进入动态查询。新增范围仍需正确发布，未命中及不能证明稳定的范围保持原查询。不能只缓存一个地址曾成功的布尔值，也不能把可写/可释放内存当永久执行范围。本轮未修改该运行时逻辑。

## 高频动态入口的实际身份

bbcpu原有报告显示稳定阶段约146–149万次/秒进入自身动态执行路径。它不是现场编译次数，也不是解释器指令数或时间占比。

用本次真正生成的`scan/imports.tsv`及运行时`imports.tsv`核对，常见目标包括：

| 目标 | 末轮10秒报告的抽样估算频率 |
| --- | ---: |
| memcpy | 约23.1万次/秒 |
| scePthreadMutexUnlock | 约10.8万次/秒 |
| scePthreadMutexLock | 约10.7万次/秒 |
| scePthreadSelf | 约10.5万次/秒 |
| memset | 约9.85万次/秒 |

`ldiv`也在高频列表，运行时记录为guest-linked；不能把全部目标都称为宿主HLE。报告每10秒及1/64抽样存在调度和周期抽样误差，上表不作精确逐次计数或耗时。

另外三项已从本次有效ELF的真实E9跳转及原补丁算法直接确认：

| 原入口 | 固定跳板（相对image） | 约频率 |
| --- | --- | ---: |
| HeapFree 0x20858a0 | 0x5954800 | 7.34万次/秒 |
| HeapPlain 0x2085730 | 0x5954820 | 7.34万次/秒 |
| HeapAligned 0x2085a60 | 0x5954840 | 7.14万次/秒 |

三项合计约21.8万次/秒。17个原函数的修改已纳入静态输入，所以没有重新发生摘要失配；但这些映像外的补丁跳板仍走动态执行，不能把“原函数准入”当成“其全部调用链都是静态”。现有导出器只导出主ELF的可靠加载/展开目录，尚未把这类owned辅助代码纳入可编译目录。

另一候选是将已验证的导入/固定跳板接入已有HLE调用桥，避免每次执行一段动态x86小桩。必须保留SysV参数/返回、寄存器/flags、嵌套回调、F3退出语义与完整owned输入依据；不得开放任意宿主指针、跳过范围检查或使用FEX混合兜底。本轮只定位，未启用快路。

## 共有门控与游戏自旋

`BbPayload::Gate::Mutation`路径在bbcpu主游戏线程占160/1009（15.86%），FEX占175/826（21.19%）。两边都有，它保护原分配/释放与GPU生命周期观察的时序，不能将其当成bbcpu独有问题或直接关闭。查询锁、资源hook祖先可能重叠，不能将百分比加成FPS预算。

bbcpu中最大的单个静态函数self热点为`f_20368c0`（全线程合计774个self样本）。原始232字节x86函数经定向反汇编确认包含scePthreadSelf、RDTSC、LOCK CMPXCHG及超时后等待，属于定时自旋/锁竞争逻辑；不是着色器编译。它在主线程占42/1009（4.16%），角色工作线程约8–9.5%。先减少接入层争锁可能降低连带自旋，但尚未证明因果或收益，不能删掉游戏锁。FEX未开启客体JIT代码地图，部分栈为未知JIT页，本轮不声称已逐函数比较静态代码和FEX生成代码质量。

## 工具、验证与下一步

复用原启动器收据、隔离克隆、Continue输入与监护流程，新增仅开发工具的显式bbcpu/FEX诊断模式；默认benchmark仍拒绝额外诊断环境覆盖。采样仅定位当前受控树中实际选中的CPU，准备器/其它路径不参与；诊断失败或中止不能作为通过，独立标注`profiler=true/performance_sample=false`。逐线程解析器用正反例验证self守恒、递归去重、重复线程段及FEX查询识别。
