# 加载内存压力的现有证据

只读比较上一轮 A4 暖入口与当前 E8 冷、暖入口；没有启动游戏、修改缓存或调整回收策略。相关保护维持原值。

## 能确认的阶段

当前冷入口的404条管线准备在385.63秒结束，准备阶段交换增量0；GPU游戏进程首次在419.60秒被采样，压力2/4首次分别在423.16/423.43秒出现。423.68秒的交换比起点增加1320.375 MiB，触发原快速增长保护；没有场景帧率结果。

当前暖入口的416条管线准备在175.27秒结束，准备阶段交换增量0；GPU游戏进程首次在234.44秒被采样，压力2/4首次在238.26/243.91秒出现，244.69秒回到2。严重压力的这段采样跨度约0.78秒，未到持续5秒停止条件。整轮交换增加856.625 MiB。

因此，两次直接压力上升都发生在游戏进程与GPU宿主实际加载阶段，而非目录准备阶段。它不证明准备器、驱动缓存或系统其它进程绝对没有影响。

## 原分类统计提供的额外限制

旧暖入口与当前暖入口均有21组周期性分类报告。**开头两组的全部八类统计逐字相同**，包括分配字节、对象数、retired、discarded、累计释放与峰值；相应的 `metal-allocated`、`owned`、guest alias capacity、unclassified Metal也全部相同。当前被保护停止的冷入口第一组同样相同。

第一组由buffers 168.44 MiB、staging 48 MiB、render-targets约40.70 MiB组成；sampled textures等其余类别为0。Guest alias capacity为4,812,046,336字节，覆盖CPU拥有的guest页，**不能再作为额外显存与CPU内存相加**。

最后一组中，旧/新sampled textures同为约320.28 MiB、1340对象；新render targets和staging容量反而较小。不过这些是独立运行的周期样本，不能据此归因某项节省，也不能把discarded容量当作常驻内存。

原进程采样中，旧/新游戏主进程footprint峰值约3362.03/3344.53 MiB；GPU宿主约2824.32/2652.77 MiB。峰值出现在各自不同时间，两个峰值不能直接拼成同时占用，更不能当作去重物理内存。当前数据没有显示这些**已观测类别**新增大块保留，但不能排除未归类、采样间峰值或系统级负担。

## 仍然缺什么

- 分类日志没有单调时间戳，只有报告顺序，不能把第N组强配到某个压力采样。
- 正常性能队列没有同步记录全系统压缩、wired、swap I/O页计数或其它进程，因此不能将交换增长归因到游戏、驱动或后台某一个进程。
- 两轮不同时间的系统起始swap分别约7248.69和8407.25 MiB；只有相同内容、补丁、设置和相机，并不足以证明系统内存条件匹配。

下一步应先复用现有只读 `NativeVMObserver`，补充加载阶段的系统级VM计数和对齐的资源报告；单独标为内存诊断，不混作性能收益证据。在获得分配/生命周期证据前，不修改缓存预算或资源回收逻辑。

公开汇总：`evidence/startup-memory-attribution-20261026/summary.json`。原始私人运行日志和完整分类分析不上传。

## 暖场景帧时间的补充计算
